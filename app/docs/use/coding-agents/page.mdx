# Coding Agents

Run Claude Code or Codex through Omnigent with a single command. No YAML needed.
You get the full platform on top of the coding agent you already use: web UI,
persistent sessions, team collaboration, mobile access, and
[contextual policies](/docs/policies/overview).

```
omni claude    # Claude Code
omni codex     # Codex
omni goose     # Goose
omni hermes    # Hermes
omni copilot   # GitHub Copilot (SDK harness)
omni devin     # Devin
```

Each command launches a built-in agent — no registration step required. Goose,
Hermes, and Devin boot their own native terminal UI in a pane, wrapped with
Omnigent's web UI, collaboration, and policy layer. `omni copilot` is shorthand
for `omni run --harness copilot` and needs the Copilot SDK (`copilot` extra); see
[GitHub Copilot](/docs/build/harnesses/configuration#github-copilot) for launch
and auth details. See [Harnesses](/docs/build/harnesses) for the full list of
coding agents and their harness ids.

Under the hood, each coding agent runs as a **harness**: the runtime that
executes your agent loop. Omnigent wraps it with a common interface and adds
everything a single harness can't provide on its own.

**[Follow the Coding Agent tutorial](/quickstart/coding-agent)** to get started
in under a minute.

## Import existing chats

Already have local Claude Code or Codex history? Bring it into Omnigent as a
normal session with `omnigent import`. The source transcript is converted to
ordinary Omnigent items and stored as a regular session, so it gains the web UI,
persistence, collaboration, and everything else. A given source session can only
be imported once unless you pass `--force` to replace the previous import.

Import a single chat by its harness-native session ID:

```
omnigent import --harness claude --session <session-id>
omnigent import --harness codex --session <session-id>
```

Or import a batch of your most recent chats with `--last N`, which imports the
`N` most recently modified parent sessions (oldest first, up to a maximum of
100):

```
omnigent import --harness claude --last 10
```

Provide exactly one of `--session` or `--last` — they are mutually exclusive.

To pull recent chats from every supported harness at once, pass
`--harness all` together with `--last N`. This merges all harnesses into a
single global recency order and imports the `N` most recent sessions in total
(not `N` per harness), each tagged with its own source:

```
omnigent import --harness all --last 25
```

`--harness all` requires `--last` — a single `--session` ID belongs to exactly
one harness, so combining `all` with `--session` is a usage error.

Re-importing a source session that was already imported is rejected by default.
Pass `--force` to replace the previous import instead — Omnigent deletes the old
conversation and re-imports the transcript in place, keeping the same session
ID:

```
omnigent import --harness claude --session <session-id> --force
```

When importing a batch, sessions that were already imported are skipped and a
session that fails to import doesn't stop the rest. Omnigent prints a summary of
how many sessions were imported, already imported, and failed, and exits with a
non-zero status if any failed.

### Import from the web UI

You can also import from the web UI without touching the terminal. Open
**Settings › Import sessions** and pick one of your online machines. The
**Import** selector offers two modes:

- **Recent sessions** — choose a harness (or **All harnesses**) and how many
  recent sessions to pull (25, 50, or 100).
- **Session by ID** — choose a specific harness and enter one harness-native
  session ID to import just that transcript, without listing your local
  history. **All harnesses** isn't available in this mode, since a session ID
  belongs to exactly one harness.

Then click **Import**. The transcripts live on your machine, so the read
happens on that connected machine over its tunnel — the server never sees your
local files. Sessions already imported are skipped, and each newly imported
session is linked in the result so you can jump straight into it.

A brand-new account with no sessions yet also gets a one-click **Import your 25
most recent sessions** button on the empty home screen (importing across all
harnesses from your online machine), plus a **Choose what to import** link into
the Settings picker. Importing from the web UI requires an online machine —
start one with `omnigent host` from your terminal if none are connected.

## Review what your harnesses bring over

Chats aren't the only thing that carries over. When one of your machines is
connected, Omnigent sessions on it already load the logins, MCP servers,
skills, and plugins you've configured in the harnesses installed there. The web
UI's **Your imports are ready** dialog shows you exactly what that is, per
harness, so nothing arrives as a surprise.

The dialog is **review only**: there are no checkboxes and nothing to opt in to.
Everything it lists carries over automatically; **Confirm** (or closing the
dialog) just acknowledges it and changes nothing on the machine.

### When it opens

- **Automatically, once per machine.** The first time a browser sees one of
  your machines online, it checks what the machine's harnesses bring. If there
  is anything to show, the dialog opens on its own. Confirming or dismissing it
  marks that machine as reviewed on this device (the memory is per browser, so
  a different browser or device will show it once more). A machine with nothing
  to show is skipped silently and rechecked the next time the app loads. The
  dialog doesn't appear when the web UI is embedded in another surface.
- **On demand, from Settings.** Open **Settings › Import sessions** and scroll
  to **Harness imports**. Each of your online machines is listed with a
  **Review imports** button that reopens the dialog for that machine. If none
  of your machines are online, the panel tells you to start one with
  `omnigent host`.

When you have more than one machine, the dialog names the one it's describing.

### What it shows

One tab per harness family detected on the machine — **Claude Code**
(`claude-native`), **Codex** (`codex-native`), and **Cursor**
(`cursor-native`) — for harnesses whose CLI is installed there. Within a
harness tab:

- **Login** — a one-line summary when the harness is signed in on that machine:
  **Databricks AI Gateway** when its inference goes through the gateway,
  otherwise **Signed in**.
- **MCP servers** — the harness's user-level MCP servers, as reported by the
  machine. Servers bundled by a plugin are labelled with that plugin
  (`<plugin> plugin`), and remote servers show their hostname.
- **Skills** — the harness's user-level skills (its home-directory catalog, the
  same one the composer's skills menu uses). Each is shown the way you'd invoke
  it in a session: `$name` on Codex, `/name` on every other harness.
- **Plugins** — skills namespaced `<plugin>:<skill>` are grouped under their
  plugin with a skill count, together with any plugin that only contributes MCP
  servers.

Only lists with something in them are shown; a harness with a login but no
assets reads **No MCPs, skills, or plugins detected**. Nothing here is edited or
copied — the dialog reads from the machine over its tunnel and the server never
sees your local files.

### Loading, offline, and partial results

- While the machine is still reporting, the dialog shows **Checking your
  harnesses…** and fills in once the inventory arrives.
- If the machine goes offline, the dialog says so and asks you to reconnect it
  to review its imports.
- If the machine could read one kind of asset but not another, what did load is
  still shown and a notice names what couldn't be read — for example
  **Couldn't read MCP servers from this machine.**
