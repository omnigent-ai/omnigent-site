# Desktop App

The Omnigent desktop app gives you the full
[web UI](/docs/interact/web-ui) in a native window, plus OS-level features
a browser can't provide: notifications when your agent needs attention, a dock badge
showing how many sessions are waiting, and multiple independent windows.

## Why use it over the browser?

- **OS notifications.** Get notified when an agent finishes, asks for input, or a runner disconnects. Notifications show the first few lines of the agent's message and only fire for sessions you're not actively viewing.
- **Dock badge.** See at a glance how many sessions need your attention, without switching to the app.
- **Multiple windows.** Open additional windows with `Cmd+N` to watch multiple sessions or servers side by side.
- **One-click host reconnect.** When a session's host is this machine and it has gone offline, the app restarts the host for you instead of asking you to run a command in a terminal.

Everything else (sessions, file editor, inline comments, collaboration) works exactly the
same as the web UI.

Refs from a snapshot are far more stable than CSS selectors against generated class
names and Shadow DOM, so the usual flow is: `browser_navigate`, then `browser_snapshot`
to see what's on the page, then `browser_click` / `browser_type` using the refs it
returned.

Because the browser runs inside the desktop window, these tools require the Omnigent
desktop app to be running with the session open. If no desktop window is subscribed,
the action fails cleanly with `browser action timed out — is the session open in the
Omnigent desktop app?` rather than hanging.

### Local network permission

Sites in the embedded pane can ask for **local network access** — for example a
sign-in page that talks to a loopback helper such as Okta Verify. When they do,
a compact Chrome-style popover appears beneath the browser toolbar, asking
**Allow local network access?** for the requesting origin, with three choices:

- **Allow once** — grants access for this site visit in this pane. It survives
  reloads and same-origin navigation, and expires when you leave the site or
  close the pane.
- **Always allow** — remembers the decision for this exact origin across all
  conversations and app restarts.
- **Deny** — blocks the permission for this origin across all conversation
  browsers and app restarts.

Closing the popover, pressing <kbd>Esc</kbd>, or clicking outside it dismisses
the request without saving a decision; the site isn't asked again until the
next navigation. Only the visible, active pane can open a new prompt, but an
existing **Allow once** or **Always allow** grant stays in effect while the
site is in the background. HTTPS sites and HTTP loopback pages can request
access; embedded subframes cannot request it on their own.

Some sign-in flows check the permission before requesting it. Because Electron
can only answer such checks with allowed or denied — never "prompt" — the popover
then shows **Allowing will reload this page**, and either allow button reloads
the page so the site retries with the new answer. If a background page has
already given up on its sign-in flow, bring its pane into view and reload.

Saved choices live in the desktop app's `settings.json` under
`browser_local_network_permissions`, as a map of origin → `true`/`false`. To
reset a saved choice, quit the app, remove that origin's entry, and reopen it.
These choices don't change the pane's per-conversation cookie and storage
isolation, and camera, microphone, notifications, and all other browser
permissions remain denied.

This controls Chromium's local-network permission answers — it is **not a
network firewall**. Not every Electron version gates every local-network fetch
on this permission, and approving it doesn't bypass CORS, TLS certificate
validation, or the agent's navigation policy. A local helper that rejects the
site through its own CORS policy must itself be configured to allow it; the pane
doesn't rewrite those headers.

## Prerequisites

- **A running server.** The [server](/docs/deploy/overview) stores your sessions and serves the UI the desktop app connects to; run it locally with `omni server start` or point the app at a deployed URL.
- **At least one runner.** A [runner](/docs/deploy/overview) is the process that actually executes your agent. If you have [cloud sandbox hosts](/docs/deploy/cloud-sandbox-host) set up, you'll be able to launch them from the app. Otherwise, register your machine by running `omni host` from your CLI.

1. **Launch the app.** On first launch, you'll see a setup screen.
2. **Enter your server URL.** `http://localhost:6767` if running locally, or your deployed server URL (e.g. `https://your-app.onrender.com`).
3. **Start working.** The app connects and shows the same UI you'd see in a browser.

The setup screen's action button tells you what will happen. A remote server
shows **Open Omnigent**: the app connects to it directly and never installs the
Omnigent CLI on this machine, since a remote server doesn't need one. Only an
explicit local setup installs the CLI — picking the local installation
(`http://localhost:6767`) shows **Install Omnigent** when the CLI is missing, and
choosing to run agents on this machine during setup installs it before
connecting (in-app install is offered on macOS). Managed servers opened from
**Join your team** behave like any other remote server: no CLI install.

## Work with multiple servers

Each window connects to one server. To work with multiple servers at the same time:

1. Go to **Server > New Window on Different Server**
2. Enter the URL of the second server

Notifications and badge counts are combined across all connected servers.

## Managed servers (macOS MDM)

On macOS, administrators can publish a list of server URLs through MDM
[Managed Preferences](https://support.apple.com/guide/deployment/welcome/web),
so people can pick their organization's server instead of typing it. The
preference domain is the desktop app's bundle identifier:

```text
ai.omnigent.desktop
```

Set the `serverUrls` key to an array of server URLs, most-preferred first:

  <thead>
    <tr>
      <th>Key</th>
      <th>Type</th>
      <th>Required</th>
      <th>Default</th>
      <th>Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>
        <code>serverUrls</code>
      </td>
      <td>Array of strings</td>
      <td>No</td>
      <td>
        <code>[]</code>
      </td>
      <td>
        Server URLs to offer, most-preferred first. Each must use{" "}
        <code>https://</code>. At most 10.
      </td>
    </tr>
  </tbody>
</table>

A schemeless host is accepted and interpreted as `https://`. Paths are
preserved, so an administrator can point directly at a workspace mount such as
`https://my-workspace.cloud.databricks.com/ml/omnigents`. Entries that share an
origin are collapsed, keeping the first. If any entry is an invalid type,
insecure, or malformed — or the list has more than 10 entries — the whole list
is rejected.

Managed servers are read only on macOS; other platforms ignore the preference.

### How they appear

Managed servers show up under **Provided by your organization** on the connect
screen and in the in-app server switcher. They are offered, not enforced:

- Omnigent never connects to them automatically.
- People can still type another server URL.
- A managed workspace path is loaded exactly as configured, rather than being
  reduced to its origin.
- Values are read from macOS on demand, not copied into the app's settings, so
  applying or removing a profile takes effect the next time the connect screen
  loads or the server switcher opens.

### Example MDM profile

Use the standard `com.apple.ManagedClient.preferences` payload with the
`ai.omnigent.desktop` application preference domain (most MDM products expose
this as a custom settings or managed preferences payload):

```xml
<key>ai.omnigent.desktop</key>
<dict>
  <key>Forced</key>
  <array>
    <dict>
      <key>mcx_preference_settings</key>
      <dict>
        <key>serverUrls</key>
        <array>
          <string>https://omnigent.corp.example.com</string>
          <string>https://my-workspace.cloud.databricks.com/ml/omnigents</string>
        </array>
      </dict>
    </dict>
  </array>
</dict>
```

### Arca hosts on Databricks-managed servers

On macOS, when an administrator has enabled Databricks-internal features
through managed preferences and the window is connected to a Databricks-managed
server, the app can connect your Arca dev instance to that server as a host —
**Run on Arca** in the new-session host picker, or the remote environment
offered during setup. The app runs the host command on the instance over
`arca ssh`, non-interactively:

```text
arca ssh -o ClearAllForwardings=yes isaac omni host --server '<server-url>' --background --non-interactive
```

A remote host needs its **own** renewable Omnigent OAuth grant. Signing in to
the desktop app in your browser, or the instance's generic Arca credentials, does
not stand in for it. When the host command reports that sign-in is required
(`OMNIGENT_AUTH_REQUIRED`, `not signed in`, or `authentication failed (HTTP 401)`
in its output), the app offers to sign in **on the instance** by running:

```text
arca ssh -o ClearAllForwardings=yes isaac omni login '<server-url>'
```

How that sign-in is offered depends on where you started:

- **Setup.** Clicking the setup action authorizes the sign-in. The setup
  terminal logs the login command, prints
  `Signing in on Arca. If a browser window opens, finish signing in there.`,
  and after a successful sign-in prints `Signed in. Connecting Arca…` and
  retries the host command once. Closing the setup window cancels a sign-in
  that only it is waiting on.
- **Connect console.** The **Run on Arca** console reports
  `This instance needs an Omnigent sign-in. Sign in through your browser, then we'll retry the connection.`
  and shows a **Sign in and retry** button. Clicking it runs the login command
  (the status line reads `Complete sign-in in your browser. Credentials stay on the Arca instance.`)
  and, on success, retries the host command once. Closing the console cancels
  the sign-in. If the retry still fails, the error is shown and no further
  sign-in is offered in that console.
- **Auto-connect.** The passive launch-time auto-connect never starts a
  sign-in. If it failed because sign-in is required, choosing **Run on Arca**
  opens the connect console so you can sign in explicitly.

Arca Companion opens the browser and routes the OAuth callback to the remote
CLI. The login command's output — which can include an OAuth ticket — is never
streamed into the app; only the outcome is shown. A sign-in that doesn't finish
within the connect timeout fails with
`Arca sign-in timed out. Check Arca Companion, finish browser sign-in, and try again.`

If the remote environment fails to start during setup, the terminal step
offers **Retry** and **Continue anyway** next to **Back**. **Continue anyway**
opens the server without the remote environment. It is only offered for a
remote-environment failure — not when the CLI install, the local-host setup, or
the connection to the server itself failed.

**Workspaces and multiple windows.** A managed server entry can select a
workspace with `/omnigent?o=<workspace-id>`; the same full server URL is used
for both the remote sign-in and the host command. Connection status, in-flight
sign-ins, and host results are tracked per full target including `?o=`, so two
workspace selectors on the same origin never share a sign-in or a host result.
Setup windows that target the same server share one in-flight sign-in: closing
one window leaves it running for the others, and closing the last waiting
window cancels it.

**Requirements.** The Arca instance must run an Isaac release that supports
Omnigent-app login (`isaac omni login`) and the `OMNIGENT_AUTH_REQUIRED`
startup diagnostic.

Relatedly, when the desktop app's host CLI is a managed `isaac omni` command,
connecting this machine as a host always runs the Omnigent login step first —
even if an existing token passes the server's auth probe — because a legacy
token can't supply the managed host's OAuth grant. A browser sign-in may
therefore open where it previously didn't.

## Open a session from a link

The desktop app registers the `omnigent://` URL scheme, so a link can open a
specific session on a specific server the way a web link opens a page. The link
names the server by host and the session by its conversation id:

```
omnigent://localhost:6767/c/conv_abc
omnigent://my-workspace.cloud.databricks.com/c/conv_xyz
```

The link carries no `http`/`https` — the app infers it the same way the setup
screen does: `http` for a loopback host (`localhost`, `127.0.0.1`), `https` for
a remote host. A Databricks workspace mount is discovered automatically, so you
don't include it in the link. Only `/c/<session_id>` links are recognized;
other paths are ignored.

Clicking a link behaves like opening a page for a known site:

- If a window is already connected to that server, the app **reuses it** and
  navigates to the session in place.
- If you've connected to that server before but have no window open for it, the
  app opens it in a **new window**.
- If you've **never connected** to that server, the app asks you to confirm
  first, since connecting to a server grants it privileges like notifications
  and registering this machine as a runner. Cancel is the default; only open
  links from servers you trust. Once you allow it, the server is remembered so
  future links open without a prompt.
