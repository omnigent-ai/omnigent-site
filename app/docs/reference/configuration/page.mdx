# Configuration reference

Omnigent configuration controls the CLI, local server, harnesses, and managed
sandboxes. These settings are separate from an agent's portable YAML spec and
from the [REST API](/reference).

## Configuration scopes

| Scope           | File or command                                                   | Use                                                                                                                                  |
| --------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Project         | `.omnigent/config.yaml` or `omni config set KEY=VALUE`            | Defaults for the current project. Project values override user values, except [user-level-only settings](#user-level-only-settings). |
| User            | `~/.omnigent/config.yaml` or `omni config set --global KEY=VALUE` | Defaults shared across projects and settings owned by the local server.                                                              |
| Deployed server | `omni server --config /path/to/config.yaml`                       | Server-wide settings for every user and session on that deployment.                                                                  |

Run `omni config list` to inspect the effective user and project configuration.
Use `omni config unset KEY` or `omni config unset --global KEY` to remove a
value from the corresponding scope.

Not every key is valid in every scope. Each setting below identifies its scope,
type, default, and validation behavior.

### User-level-only settings

Some settings are read only from `~/.omnigent/config.yaml`. A project's
`.omnigent/config.yaml` can't change them:

- **`server`**: which server the CLI connects to. Setting it without `--global`
  is rejected, and a `server` value in a project file is ignored. To use a
  different server for one command, pass `--server`.
- **`session_title_instructions`**: see
  [Automatic session titles](#automatic-session-titles).
- **Per-harness `command` and `args`** under the `harness:` key. A project can
  still select the default harness (`harness: <id>` or `harness.default`). See
  [Override the harness binary and launch args](/docs/build/harnesses/configuration#override-the-harness-binary-and-launch-args).

`omni config list` flags project-file values it ignores: user-level-only keys
appear as `# ignored user-level-only setting(s): ... (set with --global)`, and
per-harness launch entries appear as
`# ignored project harness launch overrides: ...`.

## Copy configuration between machines

`omni config cloud` saves a portable snapshot of your user-level defaults to a
server, then imports it on another machine. It copies once: later edits on
either machine stay local until you explicitly save and import again.

```sh
omni config cloud --server "$SERVER_URL" save
omni config cloud --server "$SERVER_URL" show
# On the other machine:
omni config cloud --server "$SERVER_URL" import
```

| Subcommand | Behavior                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------ |
| `show`     | Prints the saved snapshot without changing this machine.                                         |
| `save`     | Previews the saved and local values, asks for confirmation, then replaces the cloud snapshot.    |
| `import`   | Previews local and saved values, asks for confirmation, then writes the snapshot to this machine. |
| `onboard`  | Offers save or import once per server and login on interactive startup.                          |

`save` and `import` take `--yes` to confirm without prompting. If the cloud
snapshot or your login changes between the preview and the write, the command
stops and asks you to preview again. A failed request leaves the local
configuration unchanged.

`--server` defaults to `OMNIGENT_SERVER`, then the configured `server`. The URL
must be `http` or `https` without embedded credentials or a fragment. The only
supported query is the numeric `?o=` workspace selector on workspace-hosted
servers. The CLI authenticates with your normal server login, which can fall
back to ambient Databricks credentials, so use a trusted HTTPS server outside
local testing.

### What is copied

| Copied                                                                | Kept on each machine                           |
| --------------------------------------------------------------------- | ---------------------------------------------- |
| `model` and `opencode_model`                                          | Provider credentials and login tokens          |
| `harness.default` and each harness's ordered `args`                   | Per-harness `command` and host metadata        |
| Launcher plugin opt-outs, when supplied with `--plugin-opt-outs`      | Installed plugins, binaries, and project config |

- Only `~/.omnigent/config.yaml` is read and written; project
  `.omnigent/config.yaml` files are not copied.
- Harness `args` copy verbatim. Check them for secrets or machine-specific
  paths before saving.
- Import replaces the portable settings. If the snapshot has no `model`,
  `opencode_model`, or default harness, import removes that value locally.
- Copying a default harness doesn't install that harness on the other machine.
- The portable snapshot is limited to 12,000 bytes.

### Plugin opt-outs

A launcher that keeps its own plugin preferences can include them by passing
the file before the subcommand. Use the same option for `import`:

```sh
omni config cloud --server "$SERVER_URL" \
  --plugin-opt-outs "$PLUGIN_PREFERENCES_FILE" save
```

The file is JSON with `opted_out` (a list of bare plugin names, without `@`)
and `disable_all` (a boolean that freezes automatic plugin management without
removing installed plugins). Omnigent doesn't install or manage those plugins.
Without `--plugin-opt-outs`, `save` keeps any opt-outs already in the cloud
snapshot and `import` leaves local opt-outs alone. A snapshot with no opt-out
block also leaves local opt-outs unchanged.

### Import backups

Before overwriting a file, `import` writes a private backup next to it named
`<file>.before-import-<hash>` and prints its path. Backups keep the original
bytes, including any credentials, use mode `0600`, and stay until you remove
them. Imported files also use mode `0600`. If a write fails, import tries to
restore files it already wrote.

Import rewrites the YAML, so comments and formatting are not preserved, and a
symlinked config is replaced with a regular file. It also records a
`configuration_import` entry (the snapshot identity and revision) in
`~/.omnigent/config.yaml`. Each file is replaced atomically, but the config and
plugin files are not written as one transaction, so avoid editing configuration
from other tools during an import. After an interrupted import, inspect both
files and restore the printed backups if needed.

### Onboarding prompt

`omni config cloud onboard` is a hook for launchers. When a snapshot exists it
offers to import it; otherwise it offers to save this machine's configuration.
It asks once per server and login context and remembers a decline. It does
nothing unless both stdin and stdout are terminals, but it still needs a server.
Omnigent startup doesn't call it automatically. Explicit `save` and `import`
are always available.

### Server setup

| Setting | Value                                                                    |
| ------- | ------------------------------------------------------------------------ |
| Key     | `shared_preferences_authority_id`                                        |
| Scope   | Deployed server (`omni server --config`)                                 |
| Type    | Nonempty string, up to 128 characters, no surrounding whitespace         |
| Default | Unset: preference storage is disabled and the endpoint returns 404       |

Set a stable value in the server YAML to enable preference storage:

```yaml
shared_preferences_authority_id: my-omnigent-deployment
```

The CLI uses `GET` and `PUT /v1/preferences/configuration`. Snapshots are
scoped to the authenticated user and workspace and stored as one row in the
existing `preferences` table, so no migration is needed. Each save must include
the current revision. Stale saves are rejected, and no history is kept. `PUT`
bodies are limited to 16,000 bytes. Uploads that take longer than five seconds
return 408. A busy server returns 429 with `Retry-After`, and invalid bodies
return 422.

## Automatic session titles

| Setting | Value                                                |
| ------- | ---------------------------------------------------- |
| Key     | `session_title_instructions`                         |
| Scope   | User or deployed server; project values are rejected |
| Type    | String, up to 4,000 characters                       |
| Default | No additional instructions                           |

Use natural-language instructions to control the format of session titles.
These requirements apply both to titles generated from the first message in a
session and to later agent-initiated renames through the `sys_session_rename`
tool:

```
omni config set --global \
  'session_title_instructions=Prefix pull request titles with the PR number and use a short snake_case name.'
```

This setting belongs to the server, not an agent's portable instructions. It
must use the global scope for a local server. On a deployed server, set the same
key in the YAML passed to `omni server --config`:

```yaml
session_title_instructions: |
  Prefix pull request titles with the PR number.
  Use a short snake_case name for other work.
```

The generator receives the current date as `YYYY-MM-DD` along with the first
message. Default generated titles are limited to 100 characters; output beyond
that limit is rejected in favor of the first-message fallback. When custom
instructions are set, generated titles may use up to 200 characters and longer
output is truncated with an ellipsis. Manually assigned titles also have a
200-character limit.

When an agent renames a session with `sys_session_rename`, its proposed title
is formatted against these same requirements before the rename is applied. If
that formatting fails, the existing title is preserved rather than replaced by
an unformatted proposal. Without custom instructions, the agent's proposal is
used as-is. Manually assigned titles are never reformatted.

The setting applies after the local server restarts, to both new-session titles
and agent renames. An empty value removes the additional guidance. A non-string
value or a string longer than 4,000 characters is ignored and the default title
prompt is used.

## Web UI base path

| Setting | Value                                                                                |
| ------- | ------------------------------------------------------------------------------------ |
| Key     | `OMNIGENT_WEB_BASE_PATH` environment variable, or `omni server --base-path <prefix>` |
| Scope   | Server process only (environment or CLI flag); not a `config.yaml` key               |
| Type    | URL path prefix — leading slash, no trailing slash, e.g. `/proxy/6767`               |
| Default | Unset — served at the origin root (`/`)                                              |

Serves the server and web UI under a path prefix behind a reverse proxy such as
code-server's `/proxy/<port>/` or an nginx `location` block. The web UI
prefixes its API, SSE, WebSocket, and asset URLs, and the server accepts
requests with or without the prefix, so prefix-stripping and non-rewriting
proxies both work from one value. The flag is shorthand for the environment
variable and wins over an inherited value.

`""` and `/` are treated as unset. A missing leading slash is added and a
trailing slash is removed. Values that start with `//`, contain characters
outside letters, digits, and `-._~/`, include `.`/`..` segments, or whose first
segment collides with a reserved API namespace or a top-level web UI route are
rejected at startup. For the full list of reserved segments, the auth variables
to pair with it, and how the local managed server remembers the prefix, see
[Serving under a subpath](/docs/deploy/overview#serving-under-a-subpath).

## Attachment limits

| Setting | Value                                                                                                                                                    |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keys    | `filesystem_attachment_max_bytes`, `filesystem_attachment_max_files`, `filesystem_attachment_max_total_bytes`, `filesystem_attachment_denied_extensions` |
| Scope   | Server config (`omni server --config`)                                                                                                                   |
| Applies | `.zip`, `.docx`, `.xlsx`, `.pptx`, `.db`, `.sqlite`, `.sqlite3` uploads                                                                                  |

Uploads of ZIP archives, Office documents, and SQLite databases are admitted by
filename extension and stored without extraction; the harness reads a local copy
outside the working checkout (see [Attach archives, Office documents, and
databases](/docs/interact/web-ui#attach-archives-office-documents-and-databases)).
These formats require Claude Code (`claude-native`) or Codex (`codex-native`) and
an execution host/runner that supports their delivery and restoration. The
upload, copy, and fork routes apply the following limits to them:

| Key                                       | Default               | Scope                                                  |
| ----------------------------------------- | --------------------- | ------------------------------------------------------ |
| `filesystem_attachment_max_bytes`         | `52428800` (50 MiB)   | Bytes per file                                         |
| `filesystem_attachment_max_files`         | `20`                  | Stored files of these types per session                |
| `filesystem_attachment_max_total_bytes`   | `209715200` (200 MiB) | Combined bytes of these types per session              |
| `filesystem_attachment_denied_extensions` | `[]`                  | Further restrict the allowlist, e.g. `[".zip", ".db"]` |

```yaml
filesystem_attachment_max_bytes: 26214400 # 25 MiB per file
filesystem_attachment_max_files: 10
filesystem_attachment_max_total_bytes: 104857600 # 100 MiB per session
filesystem_attachment_denied_extensions: [".zip", "db"] # leading dot optional
```

Denied-extension entries are matched case-insensitively, with or without the
leading dot. Entries that are not non-empty strings are skipped with a warning;
if the value is not a list, the whole setting is ignored. The denylist can only
narrow the built-in allowlist, and it does not restrict files the agent creates
or downloads through other tools.

These are filename-based admission and storage limits, not content inspection:
the server does not identify file formats from their bytes, inspect archive
entries, or detect renamed binary content. Images, PDFs, and text/code uploads
keep their separate existing limits. The web composer also has a fixed 50 MiB
ceiling for these formats, so raising `filesystem_attachment_max_bytes` above
that has no effect for uploads made from the web UI.

**Sandbox access.** The runner writes attachment copies to
`~/.omnigent/attachments/<session-key>/<filename>` (or
`$OMNIGENT_DATA_DIR/attachments/` when overridden) on the execution host, and the
harness receives that absolute path. Custom sandbox and provider configurations
must let the runner write this cache and the harness's file-reading tools read
it; permission to read the working directory does not cover `attachments/`. If
the harness runs in a separate filesystem namespace, expose the session cache at
the same absolute path. Scope any added access to the required cache rather than
the whole data directory, which also contains credentials.

Request-phase [custom policies](/docs/policies/custom#reference-policyevent)
receive the filename and content type of these attachments with an empty `text`
value; their contents are not scanned as text.
