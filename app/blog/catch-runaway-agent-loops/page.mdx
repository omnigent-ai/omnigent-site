If you leave agents running on real work, you can now have Omnigent watch for
the moment one gets stuck and pull you in before it burns tokens going nowhere.
Two built-in guardrail policies do the watching, and neither one needs a server
model to run.

An agent that retries the exact same failing tool call, or keeps hitting errors
turn after turn, used to run until it hit a total call cap or you happened to
notice. A plain call limit cannot tell useful work apart from a spin, so it
either cuts the agent off too early or lets it churn. These policies look at
what is actually happening. `detect_loop` tracks recent tool calls and fires
when the same tool runs with identical arguments enough times inside a sliding
window. `detect_thrashing` watches tool results and fires when several calls in
a row fail or the error rate across the recent window gets too high. When either
trips, the agent pauses and you get an approval prompt explaining why, so you
can redirect it or start fresh instead of letting it grind.

Both are contextual policies you add to an agent's guardrails, and they work
with any agent you run in Omnigent. Wire them into the agent config under
`guardrails.policies`:

```yaml
guardrails:
  policies:
    loop_guard:
      type: function
      function:
        path: omnigent.policies.builtins.safety.detect_loop
        arguments:
          window: 10
          threshold: 3
    thrashing_guard:
      type: function
      function:
        path: omnigent.policies.builtins.context.detect_thrashing
        arguments:
          consecutive_threshold: 5
          window: 10
          window_error_rate: 0.8
          action: ASK
```

Tune `window` and `threshold` to how tight you want the loop check, and set
`detect_thrashing`'s `action` to `DENY` if you would rather block the next step
outright than be asked. See the
[built-in policies guide](/docs/policies/builtin) for the full parameter list.
