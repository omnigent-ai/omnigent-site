If you split big jobs across several agents, one agent can now act as the
manager. It starts worker sessions, hands each one a piece of the job, and
checks back on their results while you watch from a single place.

Until now you had to open each extra session yourself and carry context between
them by hand. Now an agent in a private session can start independent workers,
either on its own host or in a new managed sandbox. It can also send work to
other sessions you own and read their status and history. Each worker is a
regular top-level session with its own permissions and lifecycle, and its
header shows "Created by" with a link back to the manager. That way you can
always trace where a piece of work came from. If you can't access the manager,
the header just says "Created by another session" and shows nothing else.

This is on by default for sessions you keep private, so you don't need to set
anything up. Ask your agent in plain language, for example:

```text
Start two worker sessions on this host. Have one review the test coverage and
the other update the changelog. Check on both and summarize what they found.
```

The manager can also list its sessions later and pick out the workers it
started, even after a restart. Once you share a manager, it can no longer start
workers or message your other sessions, and operators can turn the feature off
server-wide. For the session tools an agent uses to do this, see
[Let an agent manage other sessions](/docs/programmatic#let-an-agent-manage-other-sessions).
