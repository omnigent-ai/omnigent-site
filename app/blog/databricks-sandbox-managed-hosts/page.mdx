If your team runs Omnigent next to a Databricks workspace, you can now pick
**New Sandbox** and have your agent start in a Databricks Sandbox that belongs
to you. The Sandbox is created and driven with your own Databricks connection,
so the agent works in the workspace as you and nobody else.

Until now, a shared sandbox setup meant handing the server one set of
credentials for everyone, which left you unable to say whose access an agent
was really using. Now every Sandbox runs under the person who started the
session. The server's own identity is never used, and there is no SSH and no
shared secret inside the Sandbox. Someone who hasn't connected their account is
asked to connect Databricks first, and no Sandbox is created for them. A
Sandbox that stops after sitting idle starts again on your next message, so a
long-running session picks up where it left off.

To try it, open **Settings → Connections → Databricks** and connect your
account. Then start a new chat and choose **New Sandbox** in the host picker.
An admin turns this on once for the server by pointing the sandbox provider at
the workspace where Sandboxes should run:

```yaml
sandbox:
  provider: databricks
  server_url: https://your-host
  databricks:
    workspace_host: https://<workspace>.cloud.databricks.com
```

The workspace needs the Databricks Sandbox preview enabled, and the server
needs an account-level OAuth app so users can connect. Keep in mind that code
in your Sandbox, including the agent, can use your token to act in the
workspace as you. The [Cloud Sandbox Host guide](/docs/deploy/cloud-sandbox-host)
covers setup end to end, and the
[Databricks settings reference](/docs/reference/configuration/cloud-sandbox#databricks)
lists every option.
